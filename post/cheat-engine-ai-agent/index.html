逆向

这两天做了一件事：不给 AI 任何提示，让它只用自己写的工具去通关 gtutorial-x86_64.exe 的关卡。

它最后打穿了两关。但比结果更有意思的是过程 —— 它连续六轮扫描都"收敛"到了一个正确答案，而那六轮全是错的。每次它都有一份看起来无可辩驳的证据，每次证据都指向错的方向。

这篇既写这六次错误，也写最后是怎么走出来的，以及那个让 AI 能自己动手的工具长什么样。

仓库：https://github.com/ip2867/CheatEngine-AI-Agent

一、先看结果

第一关的通关方式并不玄妙：弹药字段是反向映射的（屏幕显示 5，内存里是 0），锁住它，换弹永远不触发，靶子就不会回血，然后慢慢打完。

第二关有两件事值得说。第一件是代码注入：找到两个敌人和玩家共享的扣血函数 0x100042D10，读结构体的阵营字段 +0x70（玩家 0 / 敌人 1），敌人走"血量直接归零"，玩家走"完全不受伤"：

; 注入到代码洞 0x10023BB18
48 89 C8                 mov  rax, rcx
83 78 70 00              cmp dword [rax+0x70], 0
75 03                    jne enemy
C3                       ret                ; 玩家：一刀不挨
90 90
29 50 60                 sub dword [rax+0x60], edx
C7 40 60 00 00 00 00     mov dword [rax+0x60], 0   ; 敌人：一枪秒
C3                       ret

; 挂在共享扣血函数 0x100042D10 上
E9 03 8E 1F 00 90 90     jmp 0x10023BB18

但这段代码装上去之后，窗口标题变成了 Step 2 (Integrity check error)，整个战斗循环冻结 —— 子弹穿过敌人不扣血。所以那个"打不中右边敌人"的现象，根本不是瞄准问题，是它自己把游戏打坏了。

这个坑当时没被认出来，它还以为是自己算的偏角不对，花了很多轮去调瞄准几何。真正的判断只需要一句：改完代码先看窗口标题和游戏还在不在跑，再去怀疑自己的数学。

第二件是最后真正通关的那条路 —— 完全不注入代码，只用结构扫描找到三个实体，直接改血量。这条路是第七次尝试，下面第五节讲。

二、AI 为什么需要这个工具

AI 做内存分析有一个很具体的困难：它看不见进程。

它能写代码、能推汇编、能讲清楚一个 setter 每帧做了什么，但它没有办法自己按一下"扫描"。所有结论都得靠人转述，于是就变成了"我说你猜"。

把它接到 CE 上，这个断层就没了。AI 可以自己：

扫描 → 得到候选 → 打一枪 → 再扫描 → 收窄 → 下断点 → 读寄存器 → 反汇编 → 注入

整条链路闭环。这两关就是这么打下来的。

54 个工具覆盖什么

从"扫一个数值"到"注入代码区分敌我"，分十组：

分组 干什么
进程（4） 附加进程、白名单、模块段查询
读取（4） 单值读、64 KiB 批量读
扫描（6） 精确/范围/未知值基线、实时收窄、结果分页、stale 检测
分析（11） 反汇编、指针链、按结构形状扫全窗口、xref
写入（6） 带乐观锁的写、写只读页
断点（10） 硬件写断点、重装、命中记录、寄存器快照
假设与标定（6） 假设登记、锚点标定
候选集（5） 分页取候选、实时值对照
因果探针（1） 动作前后对照
审计（1） 操作留痕

完整参数和错误码在仓库的 docs/tools.md。

四个值得单独说的设计

1. scan_results 会告诉你哪些结果已经不能信了

每次返回都带 live / staleReason / changedSinceScan。所以 AI 不可能拿一份过期的快照去收窄 —— 那正是它踩过最深的坑之一。

2. 写入有乐观锁

write 要 expect，write_bytes 要 expectHex。值被外部改动时明确报 stale，而不是"写入成功"然后骗你。

这不是洁癖。没有它，你永远无法区分"我改成功了"和"我改的那一刻它已经变了"。

3. 断点会先自检

bps_arm 默认先跑 debugPathWorks(probeThreadId) 探针。调不通就直接报错，不允许你带着"断点应该在工作"的假前提继续推理。

这一条是被一个 bug 打出来的：bps_arm 少调了一次 debugProcess()，导致断点永远 0 命中，而它得出了"这台机器不支持硬件断点"这个完全错误的结论，并绕了很久。修好之后同一次会话抓到 82 次命中。

4. 抓帧会先确认没被挡住

BitBlt 是从屏幕取像素的（这个构建上 PrintWindow 全黑）。而"处于前台"只说明输入队列指向它，不说明它没被遮挡 —— 一个悬浮层、一条通知、另一个置顶窗口，都会进到截图里。

有一次"抓通关截图"，实际存下来的是一张聊天窗口。补上的是：遍历 z 序，看客户区矩形上有几个别的可见窗口，有就拒绝保存并删掉旧图。

一张自洽的错图比没有图更危险，因为下游全都信它。

三、安装

不需要管理员权限。

# 在解压后的目录里执行
powershell -ExecutionPolicy Bypass -File install.ps1

脚本做三件事：

  1. 自动找到 Cheat Engine（Program Files / 注册表 / 运行中的进程三条路）
  2. 把 ce_ai_bridge.lua 放进 CE 的 autorun/ 目录 —— CE 一启动桥就在
  3. 生成 MCP 配置片段，粘进你客户端即可

装完之后不需要手动进入 CE 界面做任何操作，管道 \\.\pipe\CE_AI_Bridge_v1_0 就在那里。

配置 MCP 客户端（以通用 JSON 为例）：

{
  "mcpServers": {
    "cheat-engine": {
      "command": "python",
      "args": ["<安装目录>/mcp/ce_mcp_server.py"]
    }
  }
}

四、六次自信的错误

下面这六件事，每一件在当时都有"实测证据"支撑。

错误一：以为"五下打死"等于"血量是 5"

这是最开始的一步，也是最贵的一步。

观察到的现象：靶子被打五下就死。于是整个搜索都围绕"血量 = 5"展开 —— 扫 5、扫减少、扫 4、3、2、1。

而真实情况是：靶子满血 188 像素，每发子弹扣 46 像素，188 ÷ 46 ≈ 4.09。也就是说它最多能挨 4 发，第 5 发是溢出伤害。血量根本不是 5。

这个错误的代价不在于数字错了，在于它把后面每一次扫描的假设都污染了。所有"扫 5 打一枪变 4"的搜索，都是在找一个不存在的东西。

教训：屏幕上"打五下死"是视觉效果，不是数值。看到"N 下死"，第一反应应该是"每下伤害多少"，而不是"血量是 N"。

错误二：以为 decreased 是个好过滤器

用 unknown 基线扫出 3300 万个候选，打一枪，筛 decreased。

筛完还剩 11 万。

这看上去是巨大的进步 —— 砍掉了 99.6%。但帧计数器、粒子计时器、动画时钟、分配器记账，全都在递减。它们永远满足 decreased。这个过滤器在物理上无法排除它们，因为它们的定义就是"一直变小"。

真正把候选砍掉 98% 的，是一次偶然的正确操作：

33,632,256  unknown 基线
  → 116,873  打一枪 decreased
  →   2,183  跨换弹 increased     ← 这一步砍掉 98%
  →      31  值落在 100..250

跨换弹的 increased —— 因为换弹会把靶子治回满血，只有真正跟血量挂钩的字段才会在这里变大。计时器们在这一步全军覆没。

教训：decreased 筛不掉计时器。一个方向的过滤永远只有一半视野，能筛掉单调递减量的过滤器，是"跨事件的 increased"，不是"事件后的 decreased"。

错误三：以为收窄可以用扫描器自己的比较

这一步的错误非常隐蔽，代码看起来完全正确。

扫描器记录候选地址时，同时记录了一份"当时的值"。收窄的时候，它拿记录的值和新扫描做比较。但 read 命令返回的是实时值。

所以两次扫描之间发生变化的字段，会主导幸存集 —— 而不是它真正想找的那个字段。

结果就是"假收敛"：候选数量一路漂亮地掉到 30 个、20 个，看起来收敛得非常好，但那 30 个和血量毫无关系。

修法只有一条：收窄必须用实时读（分页拉出 scan_results → 逐地址 read → 只保留 live 且等于目标值的）。

教训：任何"快照 + 比较"的收窄都在赌"期间没变"。而在一个每帧都在跑的进程里，这个赌注必输。

错误四：把 float 和 dword 搞反了，还连着搞反了六轮

这是最折磨人的一个。

第一关的血量，它找过 float、找过 dword、找过双向、找过比例区间 0..1，六轮全空。每一轮都很"收敛"，每一轮写进去都不生效。

真实答案是：血量是普通 32 位整数，就在 0x167BF50，从一开始就在有界窗口里面。而它一直在测的类型是 float —— 一个整数地址，用 float 去扫，永远不可能命中。

它甚至一度得出了"血量不是任何可达堆窗口里能跟随显示的普通 dword"这个结论，并写进了文档。这个结论是错的，而且它当时非常有信心。

真正的结构是这样的：

0x167BF50   dword   health          ← 权威值（整数）
0x167BF54   dword   health max      ← 除数 100
0x167C1B0   float   显示值           ← 血条画的就是这个

而那个 0x167C1B0（float 76.0）—— 它曾经很兴奋地以为自己找到了血量，因为写 38.0，血条立刻从 142 像素掉到 72 像素，正好一半。看起来完美。

但写 0.0、锁 201 次、持续 4.8 秒，游戏不判定死亡。打一枪，值自己跳回 76.0。

因为那个 setter 长这样：

0x10003EE20  48 89 C8              mov  rax, rcx
0x10003EE23  89 50 70              mov  [rax+0x70], edx      ; this->n = arg
0x10003EE2D  F2 0F 2A 40 70        cvtsi2sd xmm0, [rax+0x70]
0x10003EE32  F2 0F 2A 48 74        cvtsi2sd xmm1, [rax+0x74] ; max
0x10003EE37  F2 0F 5E C1           divsd  xmm0, xmm1
0x10003EE3B  F2 0F 59 05 ...       mulsd  xmm0, [x100.0]
0x10003EE4B  F3 0F 11 40 50        movss  [rax+0x50], xmm0   ; 目标->hp = n/max*100

显示值 = health / health_max * 100.0。它每帧都被重算一遍。 血条跟着它变，是因为游戏拿它在画血条，不是因为它就是血量的权威。

教训：一个能被你改、而且画面立刻有反应的地址，不等于它是源头。要问的是"谁每帧在写它"。能改 ≠ 有用。

另一个教训更硬：类型假设决定成败。整数地址用 float 扫，是零概率命中的搜索，而它看起来和正常搜索一模一样。

错误五：把"断点在这台机器上不可用"当成事实

中间有很长时间，它认定硬件断点在这个环境彻底废了。证据看起来很硬：

breakpoints: {'0x167C1B0': {...}}
hitCount: 0

断点装上了，读数永远是 0。它试了提权、试了换目标、试了另一种触发方式，全部 0 命中。于是写进了文档："debug_breakThread 停不住目标 ⇒ 断点路线封死"。

真因是两行代码：

bps_arm          从不调用 debugProcess()
set_breakpoint   会调用 debugProcess()

不调 debugProcess()，断点只是"登记"了，调试器根本没挂上去，所以永远不可能触发。改掉之后：

armed 1 times
bp2.hits = 82

82 次命中。 之前所有"0 命中"的结论，全部作废。

教训：“这个功能不支持"是个非常危险的结论，它会让后面所有工作绕开一个其实可用的工具。下这个结论之前，必须先证明"我调用它的方式是完整的”。

错误六：以为写进去就留住了

write 返回 verified: true，它一度以为这就成功了。

不是。verified: true 只证明这个字节落到了内存里并且回读一致，它从不证明游戏会保留这个值。

真实案例：0x6EF0129 等一批 0x210 步长的对象数组，20 个槽全部写 0，verified: true × 20 —— 血条纹丝不动。因为它是副本，游戏每帧从源头重新拷一遍。写单槽更直接：写进去 432430，立刻被覆盖成 540163（正好是下一个槽的值，说明整个数组在被批量刷新）。

教训：verified 是存储层的保证，不是语义层的保证。写完必须观察一段时间，确认它没被还原，才算数。

五、第七次：换一个问法，两个小时变一秒

前面六次错误全在同一条路上 —— 按值筛：扫一个数，打一枪，看哪个数变小了，再打一枪，再筛。

这条路能走通（第一关就是它通的），但它有一个成本结构上的死结：值在变的东西太多了。计时器、帧计数、每个对象里十几个浮点参数，全都跟着屏幕在动。而且每轮收窄都要跨几十万次管道往返，收敛到几十个候选之后还得逐个写入、截图、看血条 —— 189 个候选试到第 120 个的时候，游戏进程被拖死了。

真正的转机是把问题换了一个问法：

不要问"哪些值在按血条的方向变化"，要问"哪些相邻的两个数长得像一对血量"。

血量在实体结构里长这样：

+0x00  hp    当前血量
+0x04  max   血量上限

这两个 dword 相邻，而且必然满足 hp <= max。这不是数值规律，是逻辑约束 —— 计时器、帧计数、浮点参数都不会"碰巧"满足它。

于是扫描从"逐地址问回来"变成"在 CE 内部一次扫完整个窗口"，64 KiB 一个块，块内本地解析。实测（4 MB 窗口）：

判据 候选数
只要求 max 在 {100,200,300,500} 里 159
再加 hp <= max 6

一个约束砍掉 26 倍，被砍掉的全是 hp=301925169 max=100 这种明显垃圾，三个真实体一个没丢，耗时 0.9 秒。

而且这一秒里没有开过一枪。差分需要靠动作推进，形状扫描不需要 —— 这是它最大的优势。

顺带纠正一个更早的错误

之前在同一个窗口里用虚表指针筛实体：找 vtable == 0x002b4478 的对象。结果只找到 2 个，右敌始终找不到，于是得出了"右敌可能不在这个窗口里"的结论。

这个结论是错的。 换成形状判据之后，三个实体一次全部出现：

0x015E4B70  hp=200  max=200   ← 敌人 1
0x015E4CB0  hp=100  max=100   ← 玩家
0x015E4D10  hp=200  max=200   ← 敌人 2

间距 0x140 和 0xA0 跟历史记录完全一致。它一直都在，是判据错了。

教训很干净：用会变的东西当锚点，就是给自己埋坑。虚表值可能因为多态、不同工厂而不同；而 hp <= max 是游戏逻辑本身决定的，不随实现变化。

还有一个静默失败：批量读不是优化，是必需

用 read_memory 一次读一个值去走完 4 MB，是一百万次往返。这不是"慢一点"：

  1. 任何工具超时都跑不完（实测 3 分钟没动）；
  2. 每次往返都在目标进程上做一次读 —— 实测把游戏轮询到崩溃过。

所以桥里必须有 64 KiB 的批量读。有个细节值得写下来：返回里必须分别报告"请求了多少"和"实际读到多少"，因为跨页会提前停。按请求长度推进的话，每一页边界都会变成一个静默的数据黑洞 —— 而且它不会报错，只会让扫描结果悄悄少一块。

真正通关的写法

三个实体一次全找到之后，剩下的事就没有悬念了：

before: E1=200  PL=100  E2=200
player max → 100000   verified
player hp  → 100000   verified
E1 hp / max → 1 / 1   verified ×2
E2 hp / max → 1 / 1   verified ×2
after:  E1=1  PL=100000  E2=1

这里有个细节：两个敌人必须同时改。只改一个的话，幸存的那个会拿到伤害加成，反而更危险。

通关画面上的红字是 Player Health: 99984 —— 锁血生效了，只是掉了一点点。没有注入、没有改 .text、没有完整性检测报错。

六、还债：之前判错的部分，以及它们后来怎么了

必须写清楚，因为这个项目最容易被误解的地方就在这里。

右敌血量"找不到"

最初扫 0x01500000..0x01640000（1.4 MB），用虚表判据只找到 2 个实体（左敌尸体 + 玩家）。当时的记录是"右敌从不出现在这个扫描里"。

它一直都在。 换形状判据后三个实体一次全出来，位置和间距都对得上历史记录。这一条已经改掉了。

另外两个小坑，一并留着：

  • 0x015E4D50 的 +0x60 确实在自然衰减（195 → 194 → 193…），但它和血条显示无关，不是它的血量。“在变化"和"是它"是两件事。
  • 右敌血条是蓝色的，而当时用的像素判据只认绿色，所以一度"看不见"它 —— 这是工具的问题，不是游戏的问题。

那 9 字节的零填充

装完注入后，扣血函数后面只有 9 字节连续零，根本不够放注入体，所以必须跳到代码洞 0x10023BB18（.text 尾部 1256 字节连续零）。这个跳跃本身引入了完整性检测的风险 —— 代价已经付出了，标题变了。

这条路不是可持续策略。 真正通关用的是结构扫描，不碰代码。

桥里一个死代码

handlers.write 里原本有一个"只读页拒绝写"的检查，但 CE 7.7 的 virtualprotect / VirtualProtect / VirtualProtectEx 全是 nil，那段代码等于永远失败。已删掉，改由 writeBytes 自己做保护变更，用 expectHex 做真正的守卫。

七、15 个技能：经验变成可复用的纪律

除了工具，还带 15 个技能。这是"经验自进化"的落地形式。

2 个是这两关打出来的（自研）：

  • game-memory-hunting —— 定位字段的铁律。比如"只有跨换弹的 increased 能砍掉计时器”、“收窄必须用实时读”、"verified: true 不代表游戏保留了它"、"能按形状筛就别按数值筛"。
  • game-vision —— 从像素读状态的铁律。比如"PrintWindow 全黑时只能用屏幕 DC BitBlt"、“血条要有几何拒绝”、"前台不等于没被遮挡"。

13 个 vendored 自 awesome-game-security：反作弊架构、DMA、内核、图形 API hooking、移动端、引擎结构等技术地图。

有一点必须说清楚：那 13 个技能是纯路由索引。它们上游指向的 archive/ 正文快照有 18.6 GB，没有随仓库分发 —— 所以它们能告诉你"这个方向该看什么"，但不能当正文读。而且那是 awesome list，收录不代表技术可信，版本和环境都要自己验。

八、所以我把纪律变成了代码

这是这一轮里我认为最重要的一件事。

如果我只是在提示词里写"注意类型假设"、“注意假收敛”、“改完要观察”，那没有任何意义 —— 凡是模型可以选择不做的纪律，弱的模型一定会不做。

所以这些东西变成了工具本身的硬性约束：

曾经的错误 现在的硬约束
拿扫描快照收窄 scan_results 返回 live / staleReason / changedSinceScan，收窄只能走实时读
直接扫全地址空间 先查询模块段，扫描窗口限制在真实可写区（约 123 MB，而不是 1 亿候选）
write 成功就以为改成了 expect / expectHex 乐观锁，值被外部改动就明确报 stale
断点 0 命中还以为是环境问题 bps_arm 默认先做 debugPathWorks(probeThreadId) 探针，调不通直接报错
抓帧抓到半帧就当真值 血条三道几何拒绝 + 弹药字形解码失败即拒帧
抓帧抓到了别的窗口 z 序遮挡检测，被挡就删旧图并拒绝保存
逐地址读把进程拖死 64 KiB 批量读，返回里分开报告 requested / returned
按值筛筛到天荒地老 find_struct 按形状扫全窗口，一次调用

这些不是"建议"，是不满足就报错的接口契约。

九、AI 究竟错在哪

回头看，那些错误有一个共同结构：

每次都找到了一个"和现象相关"的东西，并把相关性当成了因果。

  • 数值"五下死" → 以为血量是 5（相关，非因果）
  • 字段"在变小" → 以为是血量（相关，非因果）
  • 血条"跟着某个 float 变" → 以为那是血量（相关，非因果 —— 那是显示副本）
  • 断点"读数 0" → 以为不支持（相关，非因果 —— 那是少了一次调用）
  • 只找到 2 个实体 → 以为第 3 个在别处（相关，非因果 —— 那是判据选错了）

能立刻改变画面的东西，不等于源头；能被观察到在变化的东西，不等于就是它。

而真正让事情翻盘的，不是"更努力地筛"，是换了一个问法。从"哪些值在按它的方向变"换成"哪些东西长得像一对血量"。前者要跟一个每帧都在动的世界搏斗，后者只需要一个逻辑约束 hp <= max。

这也是我认为整件事最有价值的地方：AI 答错的时候往往不是不够努力，而是问错了问题。 而人类指出的那句"显示值和内存值不是同向的"，本质上就是在换问题。

如果想让 AI 帮你做内存分析，这里有一套能跑、且知道自己哪里不行的接口。如果你想看"AI 怎么把自己骗了六次"，上面就是全部。
